# Étape 22 : marque par organisation dans l'application unique et le web

Source : amendement v1.2 du cahier des charges (confidentiel, hors dépôt) et décisions du fondateur. Ce document ne décrit que le socle technique ; il a servi de mission à un agent le 30 septembre 2026.

Lire d'abord la section 5 de l'amendement v1.2 et son étape 22 (critère : « deux organisations de test, deux marques, une seule application »). Décision du fondateur D11 : tout est centralisé, une seule application publiée.

## À livrer

1. **Données (migration `0022_brands`)** : table `brands` (une par organisation : `organization_id` unique, `display_name`, `logo_url`, `colors` JSONB avec `primary`, `secondary`, `background`, `text`, `accent`, `tagline`, `texts` JSONB pour les textes personnalisables, `support_phone`, `support_email`, `email_sender_name`, `email_sender_address`, `sms_sender`, `terms_url`, `privacy_url`, `updated_at`) ; table `organization_domains` (`organization_id`, `domain` unique, `kind` `booking` ou `hub`, `verification_token`, `verified_at`, `created_at`) ; colonne `organizations.join_code` (code court unique, lettres et chiffres sans ambiguïté, 8 caractères, généré à la création et pour les organisations existantes). Droits et politiques pour `neomoov_scoped` dans la même migration (voir COMMUN.md) ; fichier inverse.
2. **Domaine `packages/domain/src/branding/`** : schéma Zod de la marque, marque Neomoov par défaut (identité de `docs/design/02-prompts-claude-design.md`, prompt 0), `resolveBrand(partielle | null)` qui fusionne avec les valeurs par défaut, validation des couleurs (hexadécimal), contrôle de contraste WCAG AA (texte sur fond, texte sur couleur principale) avec message d'erreur, génération de `join_code`. Fonctions pures, testées à 100 %.
3. **API** :
   - `GET /v1/public/brand?code=<join_code>` et `GET /v1/public/brand?domain=<hôte>` (`@Public`, limité par IP, mis en cache 60 s) : thème pour les applications et le web (jamais de données personnelles).
   - `GET` et `PUT /v1/admin/organizations/:id/brand` (`@Can('brand.edit')` pour l'écriture, `organizations.read` pour la lecture ; vérifie que `brand.edit` existe dans le catalogue `packages/domain/src/access/permissions.ts`, sinon ajoute-la au module `organization` avec sa description, elle sera recopiée dans la table par les données de départ), `GET`, `POST`, `DELETE /v1/admin/organizations/:id/domains` (jeton de vérification rendu à la création ; V1 : un administrateur de la plateforme marque le domaine vérifié par `POST .../domains/:domainId/verify` après contrôle manuel du DNS, pas de vérification automatique).
   - `POST /v1/me/organizations/attach` (`@Authenticated`) avec `{ code }` : rattache le profil client de l'utilisateur à l'organisation (`clients.organization_id`), enregistre le consentement au rattachement (journal d'audit), renvoie la marque. Un client déjà rattaché à une autre organisation peut changer (une seule organisation cliente par profil en V1 ; note la limite).
   - `GET /v1/config` : ajoute `brand` (marque résolue de l'organisation du profil client de l'appelant, sinon la marque Neomoov) et `organizations` (liste courte des organisations de l'utilisateur : identifiant, nom, marque résumée) pour le sélecteur. N'écris PAS la route `GET /v1/me/organizations` (un autre agent la produit en parallèle) : lis les adhésions directement dans ton service.
4. **Applications Expo (client et chauffeur)** : fournisseur de thème qui applique la marque reçue par `/v1/config` aux jetons de design existants (couleurs, nom affiché, logo, coordonnées du support, liens des conditions), en gardant le nom sous l'icône, l'icône, l'écran de démarrage et le nom dans les notifications à « Neomoov » (limites d'Apple 4.2.6 et 4.3) ; écran « Rejoindre une organisation » (saisie du code, lecture du lien `https://neomoov.net/c/<code>` par lien profond : déclare le schéma dans `app.config.ts`) ; sélecteur d'organisation si l'utilisateur en a plusieurs. Textes i18n `fr-CA` et `en`. Types verts (`pnpm --filter @neomoov/mobile-client typecheck`, idem chauffeur) et tests unitaires existants verts.
5. **Web Next.js (`apps/web`)** : résolution de la marque par l'hôte (`Host`) dans le rendu serveur des pages publiques (`/reserver`, `/suivi`, connexion de My Hub) avec `GET /v1/public/brand?domain=` mis en cache, variables CSS pour les couleurs, logo et nom ; l'hôte inconnu garde la marque Neomoov. Types verts, tests existants verts.
6. **Courriels et textos** : quand un avis part dans un contexte d'organisation (ou pour un client rattaché), l'expéditeur affiché, le nom de marque et les coordonnées du support viennent de la marque (petit crochet `brandFor(organizationId)` dans le service des avis ; ne réécris pas ce service, un autre agent y ajoute `organization_id`). Test : deux organisations, deux expéditeurs.
7. **Tests** : domaine 100 % ; `apps/api/test/branding.e2e.test.ts` : deux organisations avec deux marques ; marque publique par code et par domaine ; rattachement par code ; `GET /v1/config` renvoie la bonne marque à chaque utilisateur ; modification par un administrateur avec la permission, refus sans ; validation des couleurs et du contraste ; dans `OrgScopeService.run(A)`, la marque de B est invisible (politique).
8. OpenAPI régénérée, `docs/decisions.md`, note `docs/reviews/etape-22-marque.md`, captures ou description des écrans dans `docs/screens/` si le dossier suit cette convention.
